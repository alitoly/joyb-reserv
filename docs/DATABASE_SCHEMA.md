# JoyB Resort — Supabase Database Schema

> Complete reference for the live reservation database (`phohqwreweaucsvsnodd`) shared between the website and the front-desk reception system.

---

## Core Principle

**The site sells room TYPES, never physical rooms.** A guest picks a type and dates; reception hands them an actual room at check-in.

---

## Tables

### 🛏️ **room_types** — Room Inventory & Pricing

Defines each bookable room category, pricing, capacity, and inventory count.

| Column | Type | Required | Notes |
|--------|------|----------|-------|
| `id` | integer | ✓ | Primary key; room type identifier |
| `name` | text | — | Room type name (e.g., "Garden View", "Suite") |
| `description` | text | — | Amenities and room description |
| `max_pax` | integer | — | Maximum guest capacity per room (adults + children) |
| `number_of_rooms` | integer | — | **Inventory count** — how many rooms of this type are available |
| `price` | numeric | — | Nightly rate in USD |

**Display Logic:**
- A room type only appears on the website when **both** `price > 0` **AND** `number_of_rooms > 0`
- Rows with `price = 0` or `number_of_rooms = 0` are hidden (half-finished entries)
- All bookings reference this table by `room_type_id`

**Example:**
```
id | name         | max_pax | number_of_rooms | price
---+--------------+---------+-----------------+-------
 1 | Deluxe       |       2 |               5 | 120
 2 | Garden View  |       4 |               8 | 150
 3 | Suite        |       6 |               3 | 200
```

### 📅 **reservations** — Booking Records

Central table for all bookings, written by both website and reception desk.

| Column | Type | Required | Notes |
|--------|------|----------|-------|
| `id` | integer | ✓ | Primary key; used to generate guest-facing reference as `JB<id>` (e.g., `JB00042`) |
| `room_type_id` | integer | — | **FK → `room_types.id`** — the type the guest actually booked; **⚠️ legacy rows may be NULL** (see Availability section) |
| `room_id` | integer | ✓ | **FK → `rooms.id`** — physical room assignment; **⚠️ TEMPORARY PLACEHOLDER** (see below) |
| `tenant_name` | text | — | Guest/tenant full name |
| `tenant_email` | text | — | Guest email address |
| `tenant_phone` | text | — | Guest phone number |
| `check_in_date` | date | — | Check-in date (ISO format: `YYYY-MM-DD`) |
| `check_out_date` | date | — | Check-out date (ISO format: `YYYY-MM-DD`) |
| `status` | text | — | Booking status; common values: `"Pending"`, `"Confirmed"`, `"Checked In"`, `"Cancelled"` |
| `total_amount` | numeric | — | Total price for stay (`room_type.price × number of nights`) |
| `adults` | integer | — | Number of adult guests |
| `children` | integer | — | Number of child guests |
| `notes` | text | — | Special requests or messages; **website bookings tagged with:** `"Source: Website"` |
| `reference_number` | text | ✓ | Internal reference (auto-generated by website to satisfy NOT NULL constraint) |
| `created_at` | timestamp | — | When the booking was created |
| `updated_at` | timestamp | — | When the booking was last modified |

**⚠️ Important Notes:**

1. **`room_id` is a temporary placeholder** — currently must be NOT NULL due to FK constraint, but it's meaningless for website bookings. The guest never chose a physical room; they chose a TYPE. Once `room_id` becomes nullable, this column will be phased out.

2. **Website vs. Front-Desk:** Distinguished via `notes` field:
   - Website bookings always include: `"Source: Website"`
   - Front-desk bookings: `notes` does not contain this tag

3. **Guest Anonymity:** Website bookings can be anonymous (guest may not provide email/phone), but tenant_name is always populated.

**Example:**
```
id | room_type_id | room_id | tenant_name      | check_in_date | check_out_date | status      | total_amount | notes
---+--------------+---------+------------------+---------------+----------------+-------------+--------------+------
42 |            1 |      7  | Alice Johnson    | 2026-08-15    | 2026-08-18     | Confirmed   |        360   | Source: Website
43 |            2 |     12  | Bob Reception    | 2026-08-15    | 2026-08-17     | Checked In  |        300   | VIP guest
```

### 🚪 **rooms** — Physical Room Master List

> ⚠️ **Mock data table — DO NOT READ for website booking logic.** This table contains test data from the reception system's early development. Prices, capacities, and row counts are meaningless.

Used **only** to satisfy the `reservations.room_id` NOT NULL constraint during checkout (temporary shim).

| Column | Type | Notes |
|--------|------|-------|
| `id` | integer | Physical room identifier |
| `room_type_id` | integer | FK → `room_types.id` |
| `day_payment` | numeric | ⚠️ **Ignore** — test data |
| `max_pax` | integer | ⚠️ **Ignore** — use `room_types.max_pax` instead |
| `status` | text | Room status (e.g., `"active"`, `"maintenance"`) |
| Other columns | — | ⚠️ **Ignore all** |

**When this table matters:**
- The `placeholderRoomId(typeId)` function queries this table to grab any room of the given type, purely to fill the `room_id` FK requirement at checkout.

**When to delete:**
- Once `reservations.room_id` becomes nullable, all references to this table can be removed from the booking flow.

### 🖼️ **room_images** — Gallery Images

> ⚠️ **Mock data table — NOT CURRENTLY USED.** All room types display a shared fallback image.

| Column | Type | Notes |
|--------|------|-------|
| `id` | integer | Image record ID |
| `room_id` | integer | FK → `rooms.id` |
| `image_path` | text | File path or URL ⚠️ Not used by website |
| Other columns | — | ⚠️ Ignore |

**Current Workaround:**
- `room_types` has no image column, so the resort's own photos are committed to `public/joyb_images/` and mapped per room type by `roomPhotosForType` (`lib/rooms.ts`). Bathrooms are a shared set, since every room's bathroom is the same design.
- To enable per-type imagery, ask the reception developer for:
  - An `image_url` or `primary_image` column on `room_types`, **OR**
  - A dedicated `room_type_images` junction table

### 👥 **tenants** — Long-Term Occupants

Tracks long-term residents (contracts > 30 days). When enabled, blocks short-term bookings if a tenant occupies the room.

| Column | Type | Notes |
|--------|------|-------|
| `id` | integer | Tenant record ID |
| `room_id` | integer | FK → `rooms.id` |
| `name` | text | Tenant name |
| `status` | text | Tenant status (e.g., `"active"`, `"moved_out"`) |
| `check_in_date` | date | Lease start date |
| `check_out_date` | date | Lease end date |
| Other columns | — | Payment, contact, etc. |

**Non-Blocking Statuses** (don't prevent website booking):
- `moved_out`, `moved-out`, `former`, `past`, `inactive`, `ended`, `terminated`

**Configuration:**
- Set `CONSIDER_TENANT_OCCUPANCY = true` in `lib/types.ts` to enforce tenant occupancy checks

## Availability Logic

**How the site prevents overbooking:**

```
Available rooms of type T for [checkIn, checkOut) 
  = room_types.number_of_rooms 
  - COUNT(reservations WHERE room_type_id = T AND blocks = true AND dates overlap)
```

**Date Overlap Rule:**
```
existing.check_in_date < new.check_out  AND  existing.check_out_date > new.check_in
```
*(Inclusive check-in, exclusive check-out)*

**Blocking vs. Non-Blocking:**

| Booking Type | Blocks Availability? | Statuses |
|--------------|----------------------|----------|
| Active | ✓ Yes | `"Pending"`, `"Confirmed"`, `"Checked In"`, any non-blocklisted value |
| Cancelled/Declined | ✗ No | `"Cancelled"`, `"Canceled"`, `"Declined"`, `"Rejected"`, `"No Show"`, `"Void"`, `"Voided"` |
| Tenant | ✓ Yes (if enabled) | Active tenant statuses exclude: `"Moved Out"`, `"Inactive"`, `"Ended"` |

**⚠️ Critical Issue:**
- **Reservations with NULL `room_type_id` are invisible to the website's availability count.**
- Legacy front-desk bookings must have `room_type_id` populated, or the website won't know they're blocking inventory.
- **Action Required:** Backfill all NULL `room_type_id` rows before go-live.

## Status Enumerations

Defined in `lib/types.ts` — centralized for consistency across website and admin.

### Hidden Room Statuses
Rooms with these statuses don't appear on the website:
- `"inactive"`, `"disabled"`, `"hidden"`, `"archived"`, `"maintenance"`, `"out_of_service"`, `"unavailable"`

### Non-Blocking Reservation Statuses
Bookings with these statuses **don't block availability**:
- `"cancelled"`, `"canceled"`, `"declined"`, `"rejected"`, `"no_show"`, `"no-show"`, `"void"`, `"voided"`

### Non-Blocking Tenant Statuses
Tenants with these statuses **don't block bookings**:
- `"moved_out"`, `"moved-out"`, `"former"`, `"past"`, `"inactive"`, `"ended"`, `"terminated"`

### Website Booking Markers
- **Tag in `reservations.notes`:** `"Source: Website"`
- **Status on new booking:** `"Pending"`
- **Status when cancelled by manager:** `"Cancelled"`

## Database Permissions

The Supabase `service_role` requires:

**SELECT:**
- `room_types` — to read inventory & pricing
- `reservations` — to check availability & display bookings
- `rooms` — for placeholder room lookup
- `room_images` — (legacy; unused)
- `pax` — (legacy; unused)
- `tenants` — for occupancy blocking

**INSERT, UPDATE:**
- `reservations` — to create new bookings & cancel (update status)

**Example SQL (run on public schema):**
```sql
GRANT SELECT ON room_types, reservations, rooms, room_images, pax, tenants TO service_role;
GRANT INSERT, UPDATE ON reservations TO service_role;
```

## Environment Variables

Set in `.env.local` (server-only, never in browser):

```bash
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_SERVICE_ROLE_KEY=your-service-role-key
```

When these are unset:
- The app gracefully degrades to read-only/stub mode
- Availability checks return "not connected"
- Booking form is disabled

## Migration Roadmap

### Phase 1: Deprecation (Current)
- `room_id` is NOT NULL (FK to `rooms.id`)
- Website uses `placeholderRoomId()` shim to fill it
- Status: **Temporary workaround**

### Phase 2: Make Nullable
- Drop NOT NULL constraint on `reservations.room_id`
- Website no longer queries `rooms` table
- Remove `placeholderRoomId()` function
- Update booking action to omit `room_id`

### Phase 3: Add Room Type Images
- Add `image_url` column to `room_types`, OR
- Create `room_type_images` junction table
- Update `lib/rooms-data.ts` to fetch per-type imagery
- Remove fallback image logic

### Phase 4: Cleanup
- Drop (or archive) `rooms` and `room_images` tables if no longer used by front desk
- Verify `room_type_id` is populated on all legacy reservations

## Quick Reference

| Need to... | Query | Notes |
|------------|-------|-------|
| List all room types | `SELECT * FROM room_types WHERE price > 0 AND number_of_rooms > 0` | Website display |
| Check availability | `SELECT COUNT(*) FROM reservations WHERE room_type_id = X AND [date overlap] AND [blocking status]` | Against inventory |
| Create a booking | `INSERT INTO reservations (room_type_id, room_id, tenant_name, ...)` | Website checkout |
| Cancel a booking | `UPDATE reservations SET status = 'Cancelled' WHERE id = X` | Admin action |
| View all bookings | `SELECT * FROM reservations ORDER BY created_at DESC LIMIT 100` | Admin list |
| Find occupant | `SELECT * FROM tenants WHERE room_id = X AND status = 'active'` | Long-term booking |
